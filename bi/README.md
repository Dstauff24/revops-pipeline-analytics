# BI layer

Four dashboards built on the SQL in this repository, plus the
export script that feeds them.

> **All data is synthetic. Generated by `data/generate.py`.
> Represents no real company or person.** Every published
> dashboard must carry this line as a visible text object, not
> just here in the README. Dashboards 01 and 03 currently do not.
> See the deviations list below.

### Known deviations from the specs, unresolved

Checked against the published views, not against Desktop. These
are blockers of varying weight and none of them is fixed yet.

**Dashboards 01 and 03 have no synthetic data disclosure.** The
rule at the top of `DASHBOARD_SPECS.md` says every dashboard
carries the line as a text object, bottom left, and calls it not
optional. 02 and 04 carry it. 01 and 03 have blank space where it
should be, and both are public right now. This is a disclosure
defect rather than a design nit, so it is first in the list and
should be first fixed. Both screenshots in `bi/screenshots/` will
need recapturing once it is, because they currently show the
version without the line.

**Dashboard 01 plots weighted coverage against a raw coverage
threshold.** Sheet 1.1 draws one reference line at 3.0 labelled
"Healthy coverage" across bars showing `weighted_coverage_x`, and
captions it "No segment has 3x weighted coverage". The 3.0 rule of
thumb belongs to raw coverage, and on `raw_coverage_x` every
segment clears it: SMB 3.03, Mid-Market 3.94, Enterprise 6.80. The
weighted threshold the spec names is 1.20, from `coverage_call` in
query 04. Against the right threshold, Mid-Market at 1.48 and
Enterprise at 2.66 are covered and only SMB at 1.13 is not, which
is exactly what the bar colors on that same sheet say, pulled from
`coverage_call`. So the sheet contradicts itself: the colors mark
two segments healthy while the line and the caption imply none is.
The caption is comparing a number to a threshold from a different
definition, which is the same error as dividing flagged dollars by
open pipeline.

**Dashboard 01 ranks segments against a shared line.** "What is
deliberately not on these dashboards" below says coverage is shown
per segment against its own threshold with no cross segment
ranking, because Enterprise deals sit open two and a half times
longer so the same health accumulates to a higher multiple. The
published sheet puts all three segments on one axis against one
line, which is the comparison that section rules out.

**Dashboard 01 is missing sheets 1.1 and 1.2 as specified.** There
is no single large coverage number; the segment bar chart stands
in its place. Aggregate weighted coverage would read 2.0x, which
is green under the spec's thresholds. There is also no open
pipeline by stage sheet: the top right chart is sheet 1.3, the
funnel over all 2,546 opportunities, and its bar lengths and
77.2 / 70.1 / 68.1 / 45.3 labels match `01_funnel_conversion.csv`
exactly. So open pipeline by stage, raw against weighted, is not
on the dashboard at all.

**Dashboard 01 sheet 1.4 is vertical and off palette.** The spec
asks stacked horizontal bars with Moving neutral grey, Slowing
amber, Stalled red. The published sheet is vertical with a purple,
pink and olive ramp. The buckets and the stacking are right.

**Dashboard 01 has layout defects.** The deal table is clipped
mid row at the bottom edge, and a floating container's close
button renders as a stray X over the first letter of the title.

**Dashboard 03 caption states a number the extract contradicts.**
The caption reads "The scalable win is Inbound at 28x on 1,000+".
Inbound returns 28.28x, which is right, on **736 leads**, which is
not 1,000 or more. No source clears 1,000 leads except Outbound at
1,798, and Outbound returns 2.38x. The argument the caption is
making survives the correction, since 736 against Referral's 249
is still the scarcity point the spec cares about, but the figure
as printed is wrong.

**Dashboard 03 is missing sheet 3.4 entirely.** The volume bars
are not on the dashboard. The spec asks for them directly under
3.1 and says the adjacency between Referral ranked first on return
and last on volume **is the argument**. The caption makes that
argument in prose instead, which is weaker and is where the wrong
number got in.

**Dashboard 03 sheet 3.3 shows won only.** The spec asks for won
and lost side by side, because lost deals die fast and that
contrast is the point, plus a reference band from `median_days` to
`p75_days`. The published sheet plots a single won median per
source with no band. The lost medians are in the extract already,
40 to 55 days against 75 to 115 for won.

**Dashboard 03 sheet 3.1 has no conditional color**, and **3.2 is
on linear axes** where the spec asks for log on both. The
breakeven reference line is present and correct.

**Dashboard 02 sheet 2.1 drops the empty `c. 80 to 99%` band.**
The spec names this one: the absence is a finding, and Tableau
must not be allowed to drop it. The published axis runs a, b, d,
e, f. The cause is upstream, `02_rep_attainment.csv` is one row
per rep and no rep carries that band, so there is nothing to pad
from and the fix belongs in the extract. Sheet 2.1 is also missing
its conditional color and its mean and median reference lines.

**Dashboard 04 renders the four no dollar checks as `$0`.** The
spec's caption note for 4.2 exists precisely to stop that reading:
unknowable is not zero. The column is also titled "Dollar
Magnitude" and shows the negative amount check as $132,500 rather
than -$132,500.

What is confirmed correct: every number checked against an
extract matched it. Dashboard 01's coverage bars are 2.660, 1.480
and 1.130 against the extract's 2.66, 1.48 and 1.13, its funnel
labels match `01_funnel_conversion.csv` step for step, and its
color split follows `coverage_call`. Dashboard 04's KPI reads
$23,050,044
with 15.0 percent of open pipeline and 471 opportunities, matching
what `export_for_bi.py` asserts, so it was built with the
opportunity condition inside the LOD. Dashboard 02's cohort chart
puts Q3 below all three other cohorts through months 01-03 and
04-06, matching the ramp assertion. Every `revenue_per_dollar` bar
and every scatter point on dashboard 03 matches
`03_channel_efficiency.csv` exactly.

### Release sequence, completed

The placeholders were a dependency loop if taken out of order: the
README needed URLs that did not exist until the workbooks were
published, and the screenshots had to come from the published
versions rather than from Desktop, because Desktop renders fonts
and sizing differently and the mismatch is visible. So, in order,
and all four steps are now done:

1. **Published the workbooks to Tableau Public**, one per
   dashboard, which is what produced the real URLs.
2. **Captured screenshots from the published views**, signed out,
   through the public render endpoint rather than a browser
   session, so no account state appears in the images.
3. **Filled in the placeholders** across this file and the root
   README, and removed the three instruction comments.
4. **Renamed the repository.**

`./check.sh` gates on all fourteen queries, the hygiene
reconciliation, the Q3 ramp assertion, the dashboard 04 dollar
figures, em dashes, and the publishing placeholders. It exits zero
as of this commit.

**What exiting zero does and does not mean.** It means nothing is
unresolved that the gate knows how to look at. It does not mean
the dashboards match their specs. The deviations listed above are
real and still open, and two of them are worth naming here because
the gate cannot see either: dashboards 01 and 03 are missing the
synthetic data disclosure that `DASHBOARD_SPECS.md` calls not
optional, and dashboard 01's coverage sheet compares weighted
coverage against a raw coverage threshold and contradicts its own
color coding. A green gate next to a known defect list is exactly
the shape `notes/BUILDING_THE_DATA.md` warns about, so the list
stays at the top of this file rather than in a scratch note.

## Why Tableau Public and not Power BI

Power BI is named in more analyst postings, so on keyword count
alone it is the better choice. It is still the wrong one here,
for a single reason: **a hiring manager has to be able to click a
link and see the dashboard.**

A `.pbix` file cannot do that. Opening one requires Power BI
Desktop installed locally, which is Windows only and which nobody
is going to install to evaluate a candidate. Publishing to the
web needs a Power BI Service tenant attached to a work account,
and a personal account cannot do it. So the Power BI artifact in
a portfolio is a binary file a reviewer downloads and cannot open,
which is worth roughly nothing.

Tableau Public is free, publishes to a real URL, and gives you a
profile page that functions as the portfolio itself. A reviewer
clicks and sees the work. That is the whole argument.

Looker Studio would also clear the link test, but "Looker" in a
posting usually means the enterprise product, which is a
different tool with a different modeling layer, so putting Looker
Studio on a resume invites a question you then have to walk back.
Not worth the ambiguity.

**The tradeoff being accepted:** everything on Tableau Public is
public, including the underlying extract. That is fine here
because the data is synthetic and disclosed as such. It would not
be fine with real CRM data, and this is not a habit to build.

**What this earns and what it does not.** After this: "built
dashboards in Tableau Public and Power BI Desktop." Not: Power BI
Service, row level security, workspace governance, administration,
or any years of experience claim.

## Why four dashboards and not one

The temptation is one dashboard with everything on it. That is a
data dump, and it reads as someone who has never had to present to
an executive who has eleven minutes.

Four audiences, four decisions, four cadences:

| Dashboard | Audience | Decision | Checked |
|---|---|---|---|
| 01 Pipeline Health | VP of Sales | Keep selling or start building | Weekly, Monday |
| 02 Rep Performance and Ramp | Sales manager | Who needs help, are new hires on track | Monthly, and at every hire |
| 03 Channel Efficiency | CMO or growth lead | Where next quarter's budget goes | Quarterly, at planning |
| 04 Data Quality Monitor | RevOps | What to fix first | Continuously |

A VP looking at pipeline coverage does not need a lead source
scatter plot on the same screen, and putting one there costs the
coverage number the attention it needed.

### 01 Pipeline Health
Coverage against quota as a single conditional number, open
pipeline by stage, stage to stage conversion, and aging buckets
split by whether a deal is still moving. Filters on territory,
segment and rep. Built on
[`queries/01`](../queries/01_funnel_conversion.sql),
[`queries/04`](../queries/04_pipeline_coverage.sql) and
[`queries/13`](../queries/13_pipeline_aging.sql).

### 02 Rep Performance and Ramp
Attainment as a histogram rather than an average, ramp curves by
hire cohort, win rate by tenure band, and a sortable rep table.
The Q3 cohort ramping slower than the others is visible on the
cohort chart, which is the point of that chart existing. Built on
[`queries/02`](../queries/02_rep_ramp_by_cohort.sql),
[`queries/06`](../queries/06_win_rate_by_segment.sql) and
[`queries/11`](../queries/11_quota_attainment_distribution.sql).

### 03 Channel Efficiency
Return on marketing spend by source with a reference line at
1.0x, cost per lead against revenue per lead, cycle length by
source, and volume. Paid sitting below the 1.0x line is the
headline: a channel that loses money is a finding with a decision
attached. Built on
[`queries/03`](../queries/03_lead_source_efficiency.sql) and
[`queries/07`](../queries/07_sales_cycle_length.sql).

### 04 Data Quality Monitor
All thirteen integrity checks ranked by severity then dollars
exposed, deduplicated dollars affected as the headline, breakdown
by issue type, and a drill down work list at record grain. Built
on [`queries/12`](../queries/12_data_hygiene_audit.sql).

The headline is deduplicated because the obvious version of it is
wrong. Summing `dollars_affected` across the thirteen checks gives
$24,552,699, but 31 opportunities fail more than one check and
their amounts are counted once per check they fail. Distinct
opportunity value behind a flag is $23,050,044, counting only
records whose check attributes dollars: the 22 deals flagged
solely by the skipped stage check are excluded, because query 12
assigns that check no dollar figure, its grain being a history row
rather than a deal. The per-check bars
keep the undeduplicated figures, because the question a single bar
answers is what fixing that check recovers, which is the deal's
whole value regardless of what else is wrong with it. The bars
overlap and the caption says so. What is not defensible is adding
them up and calling the total a headline.

The related trap is the denominator. Open pipeline is $31.1M on
dashboard 01, and $24.5M against $31.1M divides out to 79 percent
of pipeline broken, which is both alarming and meaningless: most
flagged dollars sit on closed deals. Open deals carrying a flag
are $4,666,717 of that $31.1M, or 15.0 percent. `DASHBOARD_SPECS`
sheet 4.1 carries the arithmetic and the instruction not to place
the two numbers side by side.

This is the one that is different from other portfolios. Most BI
work shows revenue charts. Almost none shows that the candidate
knows CRM data is dirty, can quantify what the mess costs, and can
hand somebody the list of records to go fix.

## What is deliberately not on these dashboards

Eight things that were considered and cut. Cutting is the part
that takes judgment; adding is free.

**1. Rep activity counts, anywhere on dashboard 02.** This is the
most important exclusion in the set. Query 09 does find that deals
worked harder in their first 30 days win more often, and it would
make a clean bar chart. It also prints `median_deal_age_days`
falling from 179 to 61 as intensity rises, which says engaged
buyers both take more meetings and move faster, so the causation
plausibly runs backwards. Put an activity leaderboard in front of
a sales manager and the response is "make more calls," which is
the one conclusion the data does not support. The finding stays in
[`ANALYSIS.md`](../notes/ANALYSIS.md) with its caveat attached.
It does not become a number somebody gets managed against.

**2. A single blended win rate.** Query 06 puts win rate between
5.6 percent (Enterprise, Outbound) and 58.1 percent (SMB,
Referral). One blended figure averages things that should not be
averaged, and it moves when the segment mix moves rather than when
performance does. Dashboard 01 shows the stage conversion chain
instead, and 02 shows the tenure cut.

**3. Average quota attainment as a headline.** Team mean is 61.7
percent, median 68.8, and the 80 to 99 percent band is empty. The
average describes nobody on the team. Dashboard 02 leads with the
histogram and puts the mean and median side by side underneath, so
the gap between them is the first thing read.

**4. Average sales cycle.** Query 07 shows the mean sitting 24 to
30 percent above the median on losses, because a long tail of
stalled deals drags it somewhere no real deal lives. Median and
p75 only.

**5. Coverage ratios compared across segments.** Enterprise runs
6.8x raw coverage against SMB at 3.0x, which reads as Enterprise
being healthier. It is not: Enterprise deals sit open roughly two
and a half times longer (169 day median won cycle against 66), so
the same health accumulates to a higher multiple. Each segment is
shown against its own threshold. There is no cross segment ranking
on that number.

**6. A forecast accuracy trend over time.** `forecast_category` is
not versioned in this dataset: it holds the last value the record
carried, not a snapshot taken at the start of the quarter. Query
05 says so in its caveat. A trend line would imply a history that
does not exist. The tenure cut is used instead, because that bias
applies roughly evenly across the bands being compared.

**7. Territory TAM penetration as a ranked bar.** `tam_estimate`
is a planning assumption somebody typed into a spreadsheet, and
the schema comment says so. Ranking territories on it presents an
opinion as a measurement. It stays as context on a tooltip, not as
a metric anyone is measured against.

**8. Deal count used as a size measure.** About 5 percent of
opportunities carry no amount, so counts and dollars disagree
systematically and the gap is not random. Wherever both appear,
the count of records missing an amount is exposed next to them
rather than left for someone to discover.

## The export layer

`python bi/export_for_bi.py` reads `pipeline.duckdb`, runs ten
queries, and writes one CSV per extract into `bi/exports/` with a
[`MANIFEST.md`](exports/MANIFEST.md) recording row count, column
count, source query and SHA256 for each.

Three things it is built to do:

**Trace every dashboard back to SQL.** The manifest names the
source query for every file. A reviewer can go from a number on a
chart to the CSV to the query that produced it without asking.

**Stay idempotent.** Two runs against an unchanged database
produce byte identical CSVs. The SHA256 in the manifest is what
makes that checkable instead of merely claimed.

**Reconcile before writing.** The record level hygiene extract is
validated against the summary extract, per check, before the
manifest is written. If the drill down and the headline ever
disagree the export fails. Two dashboards that contradict each
other is worse than no dashboard, because whichever one somebody
happens to open becomes the truth.

**Assert the ramp claim rather than eyeball it.** Both
[`ANALYSIS.md`](../notes/ANALYSIS.md) and
[`BUILDING_THE_DATA.md`](../notes/BUILDING_THE_DATA.md) state that
the Q3 hire cohort ramps slowest, and sheet 2.2 plots it. The
export asserts that Q3 sits below all three other cohorts on
pipeline created per rep month, in both bands where the planted
penalty is still live, and exits nonzero with the actual numbers
printed if it ever stops holding.

**Assert the dollar figures rather than restate them.** The
deduplicated headline of $23,050,044, the $4,666,717 of it sitting
on open deals, and the 15.0 percent ratio between that and open
pipeline are stated as literals in this file and in
`DASHBOARD_SPECS.md`. The export recomputes all three from the
extracts it is about to write and exits nonzero with actual
against expected if any has moved. Dollars are compared to within
a dollar, which is float summation noise and nothing else. The
ratio is computed and compared as a number against an explicit
plus or minus 0.05 point band, rather than rendered to the string
"15.0 percent" and matched, which would accept anything between
14.95 and 15.05 as a tolerance nobody chose and nobody could see.

That guard exists because of what this repository is. The failure
it prevents is a dashboard quietly contradicting a document whose
entire subject is catching numbers that are confidently wrong.
Checking it by looking at the chart is exactly the habit
`BUILDING_THE_DATA.md` argues against, so it is a test instead.

### Why some extracts are new files

Six extracts reuse `queries/` directly. Four live in
`bi/queries/` because a dashboard needed a grain the analysis
query had already collapsed:

| Extract | Why not the analysis query |
|---|---|
| `01_open_pipeline_deals` | Queries 04 and 13 pre-aggregate to segment and to age bucket. Dashboard 01 filters on territory, segment and rep, and a dashboard cannot filter below the grain it was handed. |
| `02_rep_attainment` | Query 11 returns six banded rows. A histogram needs the rows the bands were built from. |
| `02_win_rate_by_tenure` | No analysis query has this cut. Query 06 is segment by source, query 05 is forecast category by tenure. |
| `04_flagged_records` | Query 12 returns thirteen summary rows. The drill down needs one row per record and issue pair. |

That split is the general point. **An analysis query pre-aggregates
because it answers one fixed question. A BI extract keeps the grain
because the person reading it picks the question at view time.**
Nothing in `queries/` was modified to accommodate the dashboards,
and `run_all.py` still passes unchanged.
