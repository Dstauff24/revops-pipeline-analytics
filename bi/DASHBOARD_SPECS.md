# Dashboard build specs

Sheet by sheet build instructions for the four Tableau Public
workbooks. Written against the exact column names in
`bi/exports/`, so the build is mechanical rather than a design
exercise repeated four times.

> **All data is synthetic. Generated by `data/generate.py`.
> Represents no real company or person.**

## Rules that apply to all four

- **Disclosure.** Every dashboard gets a text object, bottom left,
  8pt grey: `Synthetic data. Generated by data/generate.py.
  Represents no real company or person.` This is not optional and
  it is not only in the README.
- **Title and subtitle.** Title is the dashboard name. Subtitle is
  one line naming the audience and the question, for example
  `For a VP of Sales: is there enough pipeline, and is any of it
  rotting?`
- **Size.** Fixed 1200 x 800. Tableau Public renders fixed sizes
  predictably and it makes the screenshots consistent.
- **No em dashes** in any title, caption, tooltip or field alias.
- **Colors.** One sequential ramp for magnitude, one diverging
  pair for good and bad against a threshold. Do not color by
  category and by measure on the same sheet.
- **Source footnote.** Bottom right, 8pt: the queries the
  dashboard is built on, for example `queries/01, 04, 13`.

## 01 Pipeline Health

Extracts: `01_open_pipeline_deals.csv` (primary),
`01_coverage_by_segment.csv`, `01_funnel_conversion.csv`.

Subtitle: `For a VP of Sales: is there enough pipeline, and is any
of it rotting?`

### Sheet 1.1 Coverage KPI
- Extract: `01_coverage_by_segment`
- Mark: Text, one large number
- Text: `SUM([stage_weighted_pipeline]) / SUM([quarterly_target])`,
  formatted to one decimal with an `x` suffix
- Color rule on that calculation: at or above 1.20 green, 0.85 to
  1.19 amber, below 0.85 red. These are the same thresholds
  `coverage_call` uses in query 04, so the number and the label
  cannot disagree.
- Caption underneath: pull `coverage_call` directly rather than
  re-deriving the wording.

### Sheet 1.2 Open pipeline by stage
- Extract: `01_open_pipeline_deals`
- Horizontal bars, Rows `stage` sorted Prospecting to Negotiation
  (manual sort, not alphabetical), Columns `SUM([amount])`
- Second bar in a lighter shade for `SUM([weighted_amount])` so
  raw and weighted sit side by side. Reps quote the raw number and
  the plan runs on the weighted one; showing both is the point.
- Label: count of deals

### Sheet 1.3 Stage to stage conversion
- Extract: `01_funnel_conversion`
- Horizontal bars, Rows `stage` in ordinal order, Columns
  `step_conversion_pct`
- Reference line at the average across stages
- Tooltip: `deals_lost_at_this_step`. The 45.3 percent at Closed
  Won is the finding; do not hide it behind a funnel shape that
  makes every step look similar.

### Sheet 1.4 Aging and momentum
- Extract: `01_open_pipeline_deals`
- Stacked horizontal bars, Rows `age_bucket`, Columns
  `SUM([amount])`, Color `momentum`
- Color: Moving neutral grey, Slowing amber, Stalled red
- Sort `age_bucket` ascending (the `a.` through `f.` prefixes in
  the data already do this)
- Tooltip: deal count, `SUM([amount])`, count where
  `owned_by_departed_rep` is true

### Dashboard filters
`territory`, `segment`, `rep_name`, applied to all sheets using
the primary extract. Coverage KPI and funnel are pre-aggregated
and will not respond to them, which is correct and worth a one
line caption saying so rather than leaving a reviewer to wonder.

## 02 Rep Performance and Ramp

Extracts: `02_rep_attainment.csv` (primary),
`02_ramp_by_cohort.csv`, `02_win_rate_by_tenure.csv`.

Subtitle: `For a sales manager: who needs help, and are new hires
ramping on schedule?`

### Sheet 2.1 Attainment distribution
- Extract: `02_rep_attainment`
- Vertical bars, Columns `attainment_band`, Rows `COUNT([rep_id])`
- Color: at or above 100 percent green, below red, split at the
  `b.` and `c.` band boundary
- Two reference lines across the sheet: team mean of
  `attainment_pct` and team median. Label both. **The gap between
  them is the reason this chart is a histogram and not a KPI.**
- The empty `c. 80 to 99%` band must render as a visible gap. Do
  not let Tableau drop it; the absence is a finding.

### Sheet 2.2 Ramp curves by hire cohort
- Extract: `02_ramp_by_cohort`
- Lines, Columns `tenure_band` (ordinal, months 01-03 through 13+),
  Rows `opps_created_per_rep_month`, Color `hire_quarter`
- Four lines, one per hire quarter. **Q3 should sit below the
  others through months 04-06.** If it does not, the extract is
  stale.
- Use `opps_created_per_rep_month` rather than `won_amount` as the
  default measure: revenue lags the behavior by a full sales
  cycle, so the leading indicator separates the cohorts earlier.
  Put `attainment_pct` on a parameter swap for the second view.
- Caption: five reps per cohort. Say the sample size on the chart.

### Sheet 2.3 Win rate by tenure band
- Extract: `02_win_rate_by_tenure`
- Bars, Columns `tenure_band`, Rows `win_rate_pct`, Color `segment`
- Tooltip: `closed_deals`, so a reader can see which bars are thin

### Sheet 2.4 Rep table
- Extract: `02_rep_attainment`
- Text table: `rep_name`, `territory`, `segment_focus`,
  `hire_date`, `tenure_band`, `prorated_quota`, `won_revenue`,
  `attainment_pct`
- Sorted by `attainment_pct` descending, and leave it sortable
- Shade the `departed` rows or add a flag column. A departed rep
  at 8 percent attainment is not the same management problem as a
  current rep at 8 percent.

## 03 Channel Efficiency

Extracts: `03_channel_efficiency.csv` (primary),
`03_cycle_by_source.csv`.

Subtitle: `For a CMO: where should next quarter's budget go?`

### Sheet 3.1 Return on spend
- Extract: `03_channel_efficiency`
- Horizontal bars, Rows `source` sorted by `revenue_per_dollar`
  descending, Columns `revenue_per_dollar`
- **Reference line at 1.0x, labelled `breakeven`.** Paid at 0.92x
  sits below it. Color bars below the line red.
- This is the headline of the dashboard. A channel that loses
  money is a finding with a decision attached, so give this sheet
  the top left position and the most space.

### Sheet 3.2 Cost against return
- Extract: `03_channel_efficiency`
- Scatter, Columns `cost_per_lead`, Rows
  `[won_revenue] / [leads]` as a calculated field, Size `leads`,
  Label `source`
- Log scale on both axes: cost per lead spans 468 to 3,072 and
  revenue per lead spans a wider range, so a linear scale collapses
  four of the five points into a corner.

### Sheet 3.3 Cycle length by source
- Extract: `03_cycle_by_source`
- Bars, Rows `source`, Columns `median_days`, Color `outcome`
- Won and Lost side by side, not stacked. Lost deals die fast and
  stacking them hides that.
- Reference band from `median_days` to `p75_days`

### Sheet 3.4 Volume and the scarcity point
- Extract: `03_channel_efficiency`
- Bars, Rows `source`, Columns `leads`
- Place this directly under sheet 3.1 so the reader sees Referral
  ranked first on return and last on volume in the same eyeline.
  **That adjacency is the argument**: the best channel is the one
  you cannot simply buy more of, so the recommendation is to fund
  a referral program rather than to move the Paid budget across.

## 04 Data Quality Monitor

Extracts: `04_data_quality_checks.csv` (primary),
`04_flagged_records.csv`.

Subtitle: `For RevOps: what is broken in the CRM, and what does it
cost?`

Build this one first and give it the most polish. It is the
dashboard other portfolios do not have.

### Sheet 4.1 Dollars exposed KPI
- Extract: `04_flagged_records`, **not** `04_data_quality_checks`
- Text mark:
  `SUM({FIXED [record_type], [record_id] : MAX([amount])})`,
  currency, no decimals. This reads **$23,050,044**.
- Second smaller line: `SUM([records])` flagged records, and the
  count of checks failing
- Do not color this one red by default. It is a standing
  operational number, not an alarm, and a permanently red KPI
  stops being read within a week.

**Why the LOD and not `SUM([dollars_affected])` off the summary
extract.** That was the original spec and it double counts. The
per-check dollars are correct per check, but 31 opportunities fail
more than one check (30 fail two, one fails three) and their
amounts are counted once per check they fail. Summing the thirteen
rows gives $24,552,699 for what is really $23,050,044 of distinct
opportunity value, a 6.5 percent overstatement. The KPI answers
"how much value sits behind broken records", and that question has
to deduplicate.

The `FIXED` key is `[record_type], [record_id]` rather than
`[record_id]` alone. Four ids collide across types in the current
extract (509, 1643 and 2539 are both an opportunity and a lead,
305 is both an opportunity and an account), and keying on
`record_id` alone silently drops one side of each collision.
Records that are not opportunities carry no amount, so they
contribute null and fall out of the sum, which is correct: the
dollars behind a duplicate account are unknowable, not zero.

**Do not put this number next to open pipeline.** $31.1M of open
pipeline is on dashboard 01, and the division is the first thing a
viewer does: $23.0M against $31.1M reads as 74 percent of pipeline
being broken, and the original $24.5M reads as 79 percent. Both
are meaningless, because they divide two different populations.
The flagged dollars are mostly on closed deals: $18,383,328 across
404 closed records against $4,666,717 across 67 open ones. The
honest comparison is that second figure, **15.0 percent of open
pipeline carries at least one flag**, and if a share of pipeline
is wanted anywhere on this dashboard, that is the one to show.

### Sheet 4.2 Ranked issue list
- Extract: `04_data_quality_checks`
- Horizontal bars, Rows `issue_type` sorted by `fix_priority`
  ascending then `dollars_affected` descending. **Match query 12's
  own ordering exactly.** Sorting by `records` instead is the
  default and it is wrong: twelve opportunities carrying a
  negative amount is a shorter list than 167 missing a loss reason
  and a much worse problem.
- Columns `dollars_affected`, Color `severity`
- Severity colors: Blocks red, Distorts amber, Cleanup grey
- Tooltip: `what_it_breaks`, `pct_of_table`, `table_affected`
- Note in the caption that three checks have no dollar figure
  (missing amount, duplicate accounts, unlinked leads) because the
  dollars are unknowable, not zero. A bar of length zero next to a
  bar of length 2.1 million reads as harmless otherwise.
- Also note in the caption that **these bars overlap and do not
  sum to the KPI in 4.1.** An opportunity failing three checks
  appears in three bars at its full amount. Per check is the right
  grain here, because the question each bar answers is "what does
  fixing this check recover", and that is the deal's whole value
  regardless of what else is wrong with it. Adding them up is what
  is wrong, which is why 4.1 deduplicates instead.

### Sheet 4.3 Breakdown by severity
- Extract: `04_data_quality_checks`
- Stacked bar or treemap, `severity` by `SUM([records])`, Color
  `severity` using the same three colors as 4.2
- Keep it small. It is orientation, not analysis.

### Sheet 4.4 Drill down work list
- Extract: `04_flagged_records`
- Text table: `issue_type`, `record_type`, `record_id`,
  `account_name`, `rep_name`, `territory`, `amount`, `detail`
- Sorted by `fix_priority` then `check_id`
- **Set sheet 4.2 as a filter action onto this sheet.** Clicking
  an issue bar filters the work list to those records. That
  interaction is the entire reason this dashboard is worth
  building rather than screenshotting the query output: the
  headline number becomes a list somebody can actually work
  through on a Friday.
- Dashboard filters: `rep_name`, `territory`, `severity`
- `detail` carries the specific problem per row, for example
  `Closed 19 days before it was created`. Leave it wide enough to
  read without a tooltip.

## After publishing

1. Replace the three placeholders in `bi/README.md`.
2. Export each dashboard as PNG at full size into
   `bi/screenshots/` using the filenames the root README expects:
   `01_pipeline_health.png`, `02_rep_performance.png`,
   `03_channel_efficiency.png`, `04_data_quality.png`.
3. Add the workbook URL to the root README's Dashboards section
   and to the GitHub repository description.
4. Run `./check.sh` before committing. It gates on em dashes
   (Tableau likes to insert them into auto generated titles), on
   leftover publishing placeholders, on all fourteen queries, and
   on the Q3 ramp assertion. It must exit zero before the repo is
   renamed or pinned.
